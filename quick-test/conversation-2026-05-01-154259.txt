⏺ 工作流节点间数据传递问题分析

  ---
  核心机制

  当前数据传递是严格的相邻节点一对一传递：

  节点 N 的 output  →  引擎存入 DataBus  →  作为节点 N+1 的 ctx.input

  引擎只做 dataBus.getOutput(stepNodes[i-1].id) →
  stepNodes[i]。没有累积，没有合并，不能跨节点取数据。

  ---
  6 个关键问题

  问题 1：相邻传递导致数据逐步丢失

  节点 A 产出 {title, price, images, description}，节点 B 只消费了 title 并产出
  {optimizedTitle}，那节点 C 收到的就只有 {optimizedTitle} —
  price、images、description 全丢了。

  实际影响（默认工作流）：
  extract-info → {title, price, images, description, brand, asin, ...}
  ai-optimize  → {optimizedTitle, optimizedDescription, seoKeywords}
                      ↑ title, images, description 全部丢失

  问题 2：阶段切换节点打断数据链

  open-shopify、open-amazon、gigab2b-crawl
  等"源节点"故意忽略上游数据，输出全新的不相关字段：

  ai-optimize  → {optimizedTitle, optimizedDescription}
  open-shopify → {shopDomain, loginStatus, adminUrl}  ← 链断了！
  fill-info    → ctx.input = {shopDomain, ...}，没有 optimizedTitle
                 ↑ 退回到默认值 '商品标题'

  同样影响 fill-info、upload-images、publish —
  它们都期望拿到上游的优化数据，但实际收到的是 Shopify 的元数据。

  问题 3：inputSchema 与实际输出字段不匹配

  下游节点: ai-optimize
  声明需要的输入: title, description, bulletPoints, longDescription, images
  上游实际输出: extract-info 输出 title, description（无
    bulletPoints/longDescription）
  匹配？: 部分匹配
  ────────────────────────────────────────
  下游节点: fill-info
  声明需要的输入: optimizedTitle, optimizedDescription
  上游实际输出: open-shopify 输出 shopDomain, loginStatus
  匹配？: 不匹配
  ────────────────────────────────────────
  下游节点: upload-images
  声明需要的输入: images
  上游实际输出: fill-info 输出 filledTitle, filledDescription（无 images）
  匹配？: 不匹配
  ────────────────────────────────────────
  下游节点: publish
  声明需要的输入: filledTitle
  上游实际输出: upload-images 输出 uploadedCount, imageUrls
  匹配？: 不匹配

  问题 4：Mock 执行器掩盖了问题

  当前大部分节点用的是 mock 执行器，它们声明了 inputSchema 但从不读取 
  ctx.input，直接返回硬编码数据：

  - extractInfoMock — 声明需要 pageTitle，但从不读取
  - publishMock — 声明需要 filledTitle，但从不读取
  - sendEmailPlugin — 声明需要 recipient, subject，但从不读取

  这意味着在 mock 模式下"流程能跑通"是假象 —
  换成真实执行器后数据链断裂会全部暴露。

  问题 5：testNode() 会清空所有上游数据

  // WorkflowEngine.ts line 38
  this.dataBus.clear();  // 每次执行都清空

  单节点测试时，DataBus 被清空，被测节点收到的是空 {}，无法验证真实的数据传递。

  问题 6：DataBus.resolve() 是死代码

  DataBus 实现了 {{nodeId.fieldName}} 模板语法，可以跨节点取任意数据。但
  WorkflowEngine 从未调用过 resolve()，这个能力完全浪费了。

  ---
  默认工作流数据链断裂图

  open-amazon     → {pageUrl, pageTitle}
                      ↓
  extract-info    → {title, price, images, description} (忽略 input，硬编码)
                      ↓
  ai-optimize     → {optimizedTitle, optimizedDescription} ✅ title/description
  传递成功
                      ↓
  open-shopify    → {shopDomain, loginStatus} ❌ 链断裂，优化数据丢失
                      ↓
  fill-info       → ctx.input = {shopDomain, ...}，退回默认值 ❌
                      ↓
  upload-images   → ctx.input 无 images 字段，空数组 ❌
                      ↓
  publish         → ctx.input 无 filledTitle，硬编码 ❌

  只有 extract-info → ai-optimize 这一段是真正在传递数据的。

  ---
  根本原因

  1. 引擎设计：一对一相邻传递，没有累积上下文
  2. 节点分类混乱："源节点"（生成新数据）和"变换节点"（消费+转换上游数据）没有区
  分，混排在同一条链中
  3. Mock 掩盖：mock 执行器不依赖 input，让断裂的链看起来正常运行
  4. 后端无编排：后端 20 个 API
  全是独立的原子操作，没有任何工作流编排能力，多步骤串联完全依赖前端

  ---
  解决方向（不修改代码，仅建议）

  1. 引擎层：改为累积式传递（每个节点收到所有上游节点的输出合集），或利用已有的
  DataBus.resolve() 模板语法
  2. 节点分类：明确标注每个节点是 source（数据源）还是
  transform（数据变换），source 节点不参与链式传递
  3. 替换 mock：逐步用真实执行器替换 mock，让数据链问题暴露出来
  4. 后端编排：考虑在后端加一个 workflow execution
  endpoint，在一个请求内串联多个服务调用，减少前端协调复杂度
